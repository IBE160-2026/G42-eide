## Intent

**Problem:** The pipeline has no first stage, so nothing yet decides from a document's actual bytes whether it is a supported PDF or plain-text file, and later stages and routes have no checked input to build on.

**Approach:** Add stage 1 in `backend/app/pipeline/`: identify the type from content (PDF signature or the ordered text rules), then check the filename extension, then open the PDF and count its pages; stop with an AD-11 code through a pipeline-level `PassFailure`, or return a typed checked document for stage 2. Document the strict-signature limitation in the README, covered by pytest with generated files.

## Boundaries & Constraints

**Always:**
- PDF only when the bytes start with `%PDF-` at offset 0; anything else goes through the text rules in this exact order: known binary signature → `unsupported_file_type`; UTF-16 or UTF-32 BOM → `bad_text_encoding`; any NUL byte → `unsupported_file_type`; strict UTF-8 decode fails → `bad_text_encoding` (one leading UTF-8 BOM allowed and removed); a disallowed control character → `unsupported_file_type` (FR-1, AR-15).
- Then the extension must match the detected type (`.pdf` / `.txt`, case-insensitive); mismatch or missing → `unsupported_file_type`. The extension alone never accepts a file.
- Then, for PDFs only: an unopenable PDF → `unreadable_file`; more than `max_pdf_pages` total pages → `file_too_large` with `limit: "pages"`. The page limit comes from the caller (settings), never a literal in the stage (AR-15).
- An empty `.txt` passes stage 1 (stage 2 rejects it later with `no_extractable_text`).
- Every test file is generated by the tests; nothing is downloaded or committed as a fixture (AR-20).
- Error codes come only from the closed list in `contracts/errors.py`; no document content, filename or exception text in any error or log line.

**Never:**
- Import `app.api` from `app.pipeline`, or change `AppError`, the error handlers or Story 1.3 code.
- Add a route, `run_pass`, stage 2 or later stages, the byte cap, `PassGuard` or any frontend change.
- Add dependencies (including `cryptography`) or change lockfiles, CI or other README sections.
- Change any logging configuration, including the `pypdf` loggers' levels, handlers or filters (decision 7), or use anything from `architecture/technology.md`.
- Touch `.claude/`, `_bmad/`, `CLAUDE.md`, `.logs/`, planning documents or `sprint-status.yaml`; stage, commit or push without the developer's approval.

## Decisions (developer, 2026-11-13, all option A)

1. **Failure:** a small `PassFailure(code, limit=None)` exception in `pipeline/`, validated against the closed code list (limit only with `file_too_large`); the api layer converts it later. `pipeline` never imports `api`.
2. **Result:** a typed checked document: for PDFs, the opened `PdfReader` and its page count; for text, the decoded text with the UTF-8 BOM removed.
3. **Order:** content first, then the extension (so a PDF named `.txt` fails before it is opened, and a UTF-16 file named `.pdf` gives `bad_text_encoding`).
4. **Encrypted PDFs:** accepted when pypdf opens them without a user password (owner-password-only); a PDF that needs a password, or whose decryption pypdf cannot perform (for example AES without `cryptography`), → `unreadable_file`. Passing stage 1 does not guarantee that stage 2 can extract text.
5. **Control characters:** disallowed are C0 (U+0000–U+001F) except tab, LF, CR and FF, plus DEL (U+007F) and C1 (U+0080–U+009F).
6. **README:** a new section `## Kjente begrensninger` with exactly: `PDF-filer må begynne med «%PDF-». Filer med ekstra bytes foran denne signaturen avvises som ikke-støttet filtype.`
7. **pypdf logging (revised at Checkpoint 1, 2026-11-13):** stage 1 leaves pypdf's logging configuration unchanged and preserves its own warnings and errors. A temporary change to the shared `pypdf` logger level was rejected because it is not concurrency-safe and `PassGuard` (Story 1.11) is not implemented yet. Narrowly scoped logging behaviour may be revisited in a later story.
8. **Extension:** the text after the last dot, lower-cased, and only when a non-empty name precedes that dot; otherwise the extension is missing (`.txt` and `notes.` are missing; `uke1.notat.TXT` is `.txt`).
9. **Displaced PDF signature (open questions 1–2, option B, 2026-11-13):** a PDF is identified only when `%PDF-` begins at byte offset 0. In the binary-signature step, a displaced `%PDF-` (the five bytes anywhere after offset 0) gives `unsupported_file_type` **only if the file would also fail one of the later text rules** (UTF-16/32 BOM, NUL byte, strict UTF-8, control characters); a valid UTF-8 text file is never rejected just because it contains `%PDF-`. This covers generated PDFs with stray leading bytes, whose binary second line fails strict UTF-8. No byte cutoff and no new dependency. Cases that cannot be told apart reliably, accepted and documented:
   - non-UTF-8 text (for example Latin-1 notes) that mentions `%PDF-` → `unsupported_file_type`, not `bad_text_encoding`;
   - a malformed file with a UTF-16/32 BOM followed by raw ASCII `%PDF-` → `unsupported_file_type`, not `bad_text_encoding` (real UTF-16/32 text cannot contain those five ASCII bytes in a row);
   - an ASCII-only PDF with stray leading bytes is valid UTF-8, so it is treated as text: named `.pdf` it is still rejected (`unsupported_file_type`, extension mismatch); named `.txt` it passes stage 1.
- **Spec length:** kept as one specification; exceeding the 1,600-token guideline is approved.
- Architecture source: `ARCHITECTURE-SPINE.md` only.

## Design Notes

- Known binary signatures (agent choice, all at offset 0): PNG `89 50 4E 47 0D 0A 1A 0A`; JPEG `FF D8 FF`; GIF `GIF87a`/`GIF89a`; ZIP/Office `PK\x03\x04`; legacy Office (OLE2) `D0 CF 11 E0 A1 B1 1A E1`. Check UTF-32 BOMs (`FF FE 00 00`, `00 00 FE FF`) before UTF-16 (`FF FE`, `FE FF`), since a UTF-32 LE BOM starts with the UTF-16 LE BOM.
- The NUL check runs on the raw bytes before decoding; the control-character check runs on the decoded text.
- pypdf's own warnings (decision 7) go to logger `pypdf._reader` and may appear in the console alongside the app's AR-26 lines. A scan of pypdf 6.21.4's warning calls found fixed, structural texts (for example "EOF marker not found") with no interpolated document content, so this does not conflict with AD-7/AR-26 ("never content"); revisit if a later pypdf version changes that.
- The displaced-signature check (decision 9) is the only binary pattern not anchored at offset 0. Simplest deterministic shape: in the binary-signature step, if `b"%PDF-"` occurs after offset 0, evaluate the remaining text rules once; if any would fail, raise `unsupported_file_type`; otherwise continue with the normal rules. The text rules must be written as one reusable check so the result is identical either way.
- Example: `validate_bytes(b"%PDF-1.7…", "uke1.pdf", max_pdf_pages=80)` → `CheckedPdf(reader, 3)`; `validate_bytes(b"\xef\xbb\xbfHei", "a.TXT", max_pdf_pages=80)` → `CheckedText("Hei")`.
