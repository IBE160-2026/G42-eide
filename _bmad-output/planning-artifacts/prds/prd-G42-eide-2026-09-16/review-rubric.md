# PRD Quality Review — AI Study Buddy (prd-G42-eide-2026-09-16)

## Overall verdict
This PRD is well-calibrated to its stakes: a small, single-workflow solo capstone project documented with real discipline rather than template-filling. Glossary, FR structure, scope boundaries, and rejected-alternatives reasoning are all doing genuine work, and there is no persona/NFR/vision theater to speak of. The only real soft spots are two done-ness gaps in FR-2 and FR-5, and one technical feasibility risk (FR-4's page-mapping) that lives only in the addendum rather than being surfaced in the PRD's own Open Questions — none of these are blocking for a project at this scale.

## Decision-readiness — adequate
Trade-offs are named with real cost, not smoothed to neutral: the Cost constraint (§8) explicitly picks a cloud LLM over local/self-hosted and states why ("simpler to implement for a first-time programmer"), and the addendum's Rejected Alternatives section names what session-only storage would have bought ("letting the student review results without immediately exporting them") against what it costs ("server-side state and retention questions"). Open Questions (§9) are genuinely open — size threshold, LLM provider/tier, tech stack, Git-workflow mapping — none are rhetorical with the answer already given.

### Findings
- **medium** FR-4's implementation risk isn't surfaced in the PRD itself (§9 Open Questions / §4.2 FR-4) — The addendum ("Open for Architecture") flags that "[p]age-level citation (FR-4) requires deliberate chunk-to-page-ID mapping; this doesn't fall out for free... worth flagging early since Page References is an MVP must-have." This is a real feasibility risk to an MVP must-have feature, but the PRD's own Open Questions list (§9, 4 items) doesn't mention it, and there's no `[NOTE FOR PM]`-equivalent at FR-4. A reader of the PRD alone would not learn that this "must-have" has an unresolved technical dependency. *Fix:* add a fifth Open Question cross-referencing the addendum's chunk-to-page-ID concern, or a short note at FR-4 itself.

## Substance over theater — strong
No theater found. There is exactly one persona-equivalent (the student/developer), consistent with the single-operator shape — no persona padding. §5 Non-Goals explicitly disclaims any differentiation ambition ("Not attempting to compete with or differentiate itself from existing commercial study tools... competitive positioning is outside this project's scope"), which forecloses innovation theater by design. Constraints (§8) are specific and falsifiable (e.g., "Zero persistence: the system must not store the uploaded Document or generated Results beyond the request/response cycle... Processed in memory only, discarded once Results are returned") rather than generic "must be scalable/secure" boilerplate. The Vision (§1) names the actual mechanism and contrasts it with named competitors (Quizlet, NotebookLM) rather than reading as swappable filler.

## Strategic coherence — strong
The thesis is explicit and consistently followed: "one well-understood workflow, built and tested end-to-end, rather than a broad feature set" (§1), with the "meta/builder" JTBD (§2.1) making process rigor itself part of the deliverable. Feature scope (§4, §6) tracks that thesis tightly — single Document, single Generation Pass, no accounts, zero persistence — with no easy-first features that don't serve it. Success Metrics validate the thesis rather than measuring activity: SM-2 (Explainability) and SM-3 (Documented process) test the process-over-output bet directly, and SM-C1 is a genuine counter-metric ("do not add Document types, output formats, or audience breadth beyond MVP In Scope to chase impressiveness") that actively guards against scope creep rather than just existing as a checkbox.

## Done-ness clarity — adequate
Most FRs carry testable consequences with real specificity — FR-1's rejection messaging, FR-4's PDF-vs-plain-text page-reference behavior ("No Page Reference is fabricated for plain-text Documents lacking page information — omitted, not guessed"), and FR-6's visibility requirement are all unambiguous. Two FRs fall short of that bar.

### Findings
- **medium** FR-2's "sensible defaults" are undefined (§4.1 FR-2) — The only testable consequence is "a Generation Pass proceeds with sensible defaults if left blank," but no default detail level or output language is specified anywhere in the PRD. An engineer can't verify this consequence without inventing the defaults themselves. *Fix:* state the actual default values (e.g., default detail level = "standard," default output language = Document's apparent language or a fixed fallback), or explicitly tag it `[ASSUMPTION]` and index it if genuinely undecided.
- **low** FR-5 has no "Consequences (testable)" subsection (§4.3 FR-5) — Every other FR (FR-1 through FR-4, FR-6) has one; FR-5 ("The student sees the Summary, Flashcard Set, Quiz, and Key Concepts in the browser after a successful Generation Pass.") does not, breaking the pattern. The FR statement is simple enough to be self-testable, but the inconsistency is worth closing for downstream story generation. *Fix:* add a one-line Consequences subsection mirroring the FR statement, for structural consistency.

## Scope honesty — strong
Non-Goals (§5) and Out of Scope for MVP (§6.2) both do real work rather than being pro-forma: each bullet in §6.2 carries its own rationale (e.g., chunking is excluded because it's "a known source of bugs (broken context, severed answers); not worth the complexity for a first project"). The single `[ASSUMPTION]` (FR-1's size threshold) is correctly tagged inline and round-trips cleanly to the Assumptions Index (§10) — nothing indexed that isn't inline, nothing inline that isn't indexed. Open-items density (4 Open Questions + 1 Assumption) is appropriately light for these stakes and doesn't read as a PRD papering over unresolved decisions. De-scoping is argued, not silent (see the session-only-storage rejection in addendum.md, which explains why a friendlier MVP option was set aside rather than just omitted).

## Downstream usability — strong
This PRD explicitly feeds Architecture and epics/stories (§0 Document Purpose), so this dimension carries real weight here, not just as a formality. The Glossary (§3) is precise and load-bearing — 8 terms, each used identically across Features, Scope, Constraints, and the addendum (e.g., "Generation Pass," "Page Reference" singular/"Page References" natural plural, "Verification Notice" all track consistently). FR IDs (FR-1–FR-6) and SM IDs (SM-1–SM-3, SM-C1) are contiguous with no gaps or duplicates, and every "Realizes UJ-1" cross-reference resolves (there is exactly one UJ, referenced consistently at each Feature and FR-1). Sections are largely self-contained via Glossary terms rather than "see above" pointers.

## Shape fit — strong
This is correctly shaped as a single-operator, single-workflow capability spec rather than forced into a heavier consumer-product template: one UJ (appropriately, not under- or over-formalized — a second or third UJ would have been padding given the JTBD already is the journey, per §2.3's own framing), no persona proliferation, and Success Metrics that are personal/self-assessed (SM-1, SM-2) rather than user-base metrics that wouldn't make sense for a solo-use tool. The three-feature-group structure (§4.1–4.3) is proportionate to scope, not thin — it matches a project this size rather than looking under-built.
